# 02 — Feature coverage

This is the target architecture for the whole product, not an audit of the outgoing database. “Planned” means a feature has repository evidence but is not assumed to be a working main-branch capability. Coverage was checked across backend routes/services/tests, iOS screens and state, the Watch companion, product documents, SQL design, and the separate LAN branch. Static landing/design/reference assets do not require their own database.

Table names below are defined in [03](03-relational-model.md) and [04](04-timescale-design.md). Unless qualified, ordinary tables are in `app`; hypertables are in `telemetry`.

## Things that do not become database jobs

- Battle animations, UI transitions, camera processing, barcode recognition, local reminders, and deterministic offline practice stay on the device where appropriate.
- Image analysis and art/lore generation remain external computation, with status/results stored in PostgreSQL.
- The database schedules/records work but does not itself supply HTTP/SSE/APNs endpoints.
- A marketing landing page and static design mockups need no access to the private application database. Add a separate narrowly scoped model only if an actual dynamic feature is requested.

## Product-rule boundaries

Current seven-tier rarity and tested calculations are the initial parity contract. Earlier descriptions of four tiers, gym reward-only buffs, duplicate-scan rewards, and currency naming are not silently promoted into new database rules. Each activation must select a `rules_version`, specify its behavior, and add tests. The tables support both keys and a separately enabled earned-capsule system without pretending they are the same balance.
